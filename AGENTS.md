# AI Agent Instructions for EmailSign Codebase

Welcome AI Agents! This document provides detailed information about the `emailsign` (formerly `mysigmail`) codebase, its structure, and the software design/coding principles you must follow when contributing to this project. You must adhere to these instructions when proposing or implementing changes.

The goal of this repository is to provide an open-source email signature generator for Gmail, Outlook, Apple Mail, etc. This is a significantly modified fork optimized for self-hosting with Docker, a pluggable storage subsystem, and an optional authentication layer.

## 1. Project Overview & Tech Stack
- **Frontend Framework**: Vue 3 (Composition API and `<script setup>` syntax)
- **Bundler**: Vite
- **Backend (Auth & Storage)**: Node.js, Express, Argon2 (password hashing)
- **Package Manager Support**: `npm`, `pnpm`, `yarn`, or `bun` (all are supported; ensure cross-compatibility).
- **Styling**: Tailwind CSS (v4) with a utility-first approach
- **UI Components**: Shadcn Vue (styled with Tailwind and `lucide-vue-next` for icons)
- **Storage Subsystem**: Pluggable support for Cloudflare R2, AWS S3, Supabase, MinIO, DO Spaces, or local Base64 fallback (via `@aws-sdk/client-s3` and `@supabase/supabase-js`).
- **Code Quality & Testing**: ESLint, Prettier, TypeScript, Lint-staged, Commitlint, Vitest, and Playwright for E2E.

## 2. Codebase Structure

Understanding the structure is key to knowing where to make changes:

- `src/`: Contains the Vue frontend client application.
  - `src/main.ts`: Application entry point. Mounts the Vue app and registers plugins.
  - `src/App.vue`: The root component for the application.
  - `src/router/`: Vue Router configuration.
  - `src/views/`: Contains main page components (e.g., `Basic.vue`, `Social.vue`, `Options.vue`, `Addons.vue`, `Templates.vue`).
  - `src/components/`: Reusable UI components (including Shadcn Vue primitives in `src/components/ui/`).
  - `src/composables/`: Reusable Vue logic (e.g., `useSignatures.ts`).
  - `src/lib/` & `src/utils/`: Helper functions and shared logic (like the `cn` utility).
- `server/`: Contains the Node.js / Express backend layer which manages authentication (`REQUIRE_AUTH`) and potential backend storage interactions (`storage.js`).
- `docker/`: Contains the Docker-first deployment architecture configurations (`docker-compose.yml`, `.caddy.yml`, `.nginx.yml`).
- `deploy/`: Contains deployment scripts or configurations.
- `docs/`: Contains extensive documentation (`DOCKER.md`, `STORAGE.md`, `SECURITY.md`).
- `e2e/`: Playwright end-to-end tests.
- `test-results/` and `playwright-report/`: Generated by Playwright.
- Configuration files (`vite.config.ts`, `tailwind.config`, `tsconfig.*`, `eslint.config.js`, `components.json`, `.env.example`) sit at the root level.

## 3. Software Design & Coding Principles

When writing or modifying code in this repository, you must adhere to the following principles:

### a) Single Responsibility Principle (SRP)
Components, composables, server routes, and utility functions should do one thing and do it well.

### b) DRY (Don't Repeat Yourself)
Extract duplicated code into utility functions, composables (`src/composables`), or reusable components (`src/components`).

### c) Fullstack Awareness
- **Frontend**: Exclusively use `<script setup>` syntax for all components. Use `ref`/`reactive` appropriately. Leverage Vue's reactivity system efficiently to avoid unnecessary re-renders.
- **Backend**: The Express server must remain lightweight. Authentication uses Argon2; always respect the `REQUIRE_AUTH` `.env` flag. Ensure API endpoints are secure and handle errors properly.
- **Storage**: When modifying storage logic (`server/storage.js`), ensure the pluggable architecture is maintained (i.e., do not hardcode AWS paths; respect the environment variables for S3, Supabase, etc.). Do not leak credentials to the client.

### d) Styling & Component Library
- Strictly use **Tailwind CSS** utility classes. Use the `cn` utility (`src/lib/utils.ts` or equivalent) for conditional classes.
- Extract complex, repetitive class combinations only when absolutely necessary.
- Use Shadcn Vue for UI elements (`pnpm dlx shadcn-vue@2.0.1 add <component>`).

### e) TypeScript & Type Safety
- The project relies heavily on TypeScript. **Do not use `any`**.
- Always define proper interfaces or types for your data structures, props, emits, state, and API payloads.

## 4. Instructions for AI Agents

When acting upon user requests, follow this workflow:

1. **Understand First**: Read the relevant files in `src/` and `server/` to trace how data flows (especially regarding signatures and image uploads). Consult `docs/` if modifying Docker or Storage.
2. **Environment**:
   - Ensure you read and respect the `.env.example` configurations.
   - Any new dependencies or script changes must be compatible across all supported package managers (`npm`, `pnpm`, `yarn`, `bun`).
3. **Docker / Self-Hosting Integrity**:
   - If you modify the build process or environment variables, you **must** update the `Dockerfile` and `docker-compose` files in the `docker/` directory, as well as relevant docs in `docs/`.
   - **Cross-Checking**: Always cross-check codebase interactions when modifying Backend/Storage features.
   - **User Permission**: Before making any architectural changes to the Backend, Storage, or Docker configurations, **notify the user, explain the issue, and explicitly ask for permission to proceed**.
4. **Testing & Verification**:
   - All new non-UI logic must have unit tests. Any new major feature/UI must have E2E tests.
   - Run unit tests: `npm run test:unit` (or package manager equivalent).
   - Run E2E tests: `npm run test:e2e` (or package manager equivalent).
   - Ensure linter passes: `npm run lint` (or package manager equivalent).
   - Always run existing tests after making changes to ensure no regressions.
5. **Commit Convention**:
   - **No Auto-Committing**: **DO NOT** commit changes autonomously unless requested by the user.
   - The project strictly uses [Conventional Commits](https://www.conventionalcommits.org/). Format: `<type>(<optional scope>): <description>`.
6. **Pre-commit Steps**:
   - Before completing tasks, always run the required linters, formatters, and tests as defined in the `package.json` scripts.

By following these instructions, you ensure this modified `emailsign` fork remains highly scalable, robustly tested, and natively self-hostable.
